## 1. Контекст и общая оценка

Это **ранний скелет**, а не незаконченный продукт, и ревью написано соответственно.
`README.md` — подробный и продуманный дизайн-документ (таймеры, эффекты, зоны спавна,
квесты, торговля, сохранения). `andor.cpp` реализует из него практически ничего:
две структуры с полями, пустые `render_map()`, `render()`, `load_char()`, заглушка
парсера карты.

Поэтому ценность ревью не в «вылизывании» кода, а в том, чтобы **зафиксировать
фундамент до того, как на него ляжет 5000 строк**. Найденные ниже дефекты — не
стилистические придирки: часть из них уже сейчас приводит к невозможности сборки,
segfault и порче стека, и все они находятся ровно в том слое (файловый I/O,
инициализация состояния, главный цикл), который будет использоваться всей игрой.

**Статус:** проект в текущем виде **не собирается ни на одной платформе**.

## 2. Блокеры — проект не собирается и не запускается

### B1. Лишняя `}` в конце файла — жёсткая ошибка компиляции
`andor.cpp:193`

`main()` закрывается на строке 192, а на 193 стоит ещё одна `}`.

```
andor.cpp:193:1: error: expected declaration before '}' token
```

Это значит, что **закоммиченный код никогда не собирался**. Первое, что стоит
завести, — CI (см. §5.13), который бы не дал такому коммиту пройти.

### B2. Противоречивые платформенные зависимости — не собирается нигде
`andor.cpp:19` (`conio.h`, `getch()`) против `andor.cpp:87,153,185` (`system("clear")`)

* `<conio.h>` и `getch()` — Windows-only (MSVC/MinGW). На Linux/macOS заголовка нет:
  ```
  andor.cpp:19:10: fatal error: conio.h: No such file or directory
  ```
* `system("clear")` — Unix-only. На Windows нужно `cls`.
* В MSVC `getch()` устарел, требуется `_getch()`.

То есть на Linux не хватает `conio.h`, а на Windows команда очистки экрана неверна.
Обе половины ввода-вывода написаны под разные ОС.

**Решение:** вынести весь платформозависимый ввод/вывод за один тонкий интерфейс
(`platform.h`: `read_key()`, `clear_screen()`) с реализациями через `termios` на
POSIX и `conio`/WinAPI на Windows. Заодно уйдёт `system()` (см. §5.9).

### B3. `update()` — пустой бесконечный цикл; это не «заглушка», а UB
`andor.cpp:156-158`

```cpp
void update() { while(1); }
```

Игра зависает сразу после «Новая игра», сжигая 100% ядра. Но проблема глубже:
цикл без побочных эффектов, volatile-обращений и I/O нарушает гарантию прогресса
C++11 ([intro.progress]) — компилятор вправе считать, что он завершается.
Результат реально расходится между компиляторами:

```asm
; g++ -O2  -> цикл сохранён, вечное зависание
_Z6updatev: .L2: jmp .L2

; clang++ -O2 -> тело удалено целиком, функция без ret,
;                исполнение "проваливается" в следующие байты
_Z6updatev:
# %bb.0:
.Lfunc_end0:
```

Под clang `gameplay()` вызывает `render()` **один раз** и уходит в неопределённое
поведение. Заглушку нужно писать как честное ожидание ввода, а не `while(1);`.

## 3. Критические — падения и порча памяти

### C1. `fclose(NULL)` при отсутствии файла → segfault
`andor.cpp:43-47`

```cpp
if ((fp = fopen(path.c_str(),"r")) == NULL) {
    fclose(fp);      // fp == NULL -> UB
    return res;
} else fp = fopen(path.c_str(),"r");   // открытие ВТОРОЙ раз
```

Проверено — воспроизводится стабильно:
```
calling ReadAllLines on a nonexistent path...
Segmentation fault (exit=139)
```

**Ветка `else` содержит второй дефект (C4):** файл уже открыт условием `if`,
и повторный `fopen` **течёт дескриптором на каждый вызов**. Достаточно
`if (!fp) return res;`.

### C2. Неинициализированные поля: `int a, b, c = 0;` инициализирует только `c`
`andor.cpp:99,101,103,134`

```cpp
int level, exp, maxexp, location, x, y = 0;   // = 0 относится ТОЛЬКО к y
```

Это одно из самых частых заблуждений C++. Замер на реальной структуре:

```
y       (последний в списке) = 0
location (в середине)        = 32638   <-- мусор
_hp      (в середине)        = 656     <-- мусор
_resist  (последний)         = 0
```

Затронуты `player` (строки 99, 101, 103) и `base_map::width` (строка 134).

### C2+C1 — достижимая цепочка до краха

Дефекты складываются в реальный сценарий падения через **пункт меню «Загрузить»**:

1. `load()` → `plr.load_char()` — **тело пустое** (`andor.cpp:123-125`), `location` остаётся мусором;
2. → `map.load_map(plr.location)` → `ReadAllLines("map/32638.txt")`;
3. файла нет → `fclose(NULL)` → **segfault**.

То есть «Загрузить» в текущем виде — гарантированный краш, а не просто пустышка.

### C3. Переполнение буфера на стеке в `WriteAllLines`
`andor.cpp:29,33`

```cpp
char tc[80];
sprintf(tc,"%s",txt[i].c_str());   // без ограничения длины
```

Любая строка ≥ 80 символов затирает стек. Для сохранений это не гипотетика:
строка инвентаря или список кодов заспавненных мобов легко длиннее. Проверено:

```
*** buffer overflow detected ***: terminated (exit=134)
```

Промежуточный буфер здесь вообще не нужен:
```cpp
fputs(txt[i].c_str(), fp);
fputc('\n', fp);
```
Также в `WriteAllLines` **нет проверки `fopen` на `NULL`** — при неудачной записи
сохранения будет то же падение, что в C1.

### C5. `char ch = getc()` + `while (!feof())` — теряется последняя строка
`andor.cpp:50-58`

Две классические ошибки сразу: `getc()` возвращает `int` (EOF = −1 не отличим от
байта `0xFF` после сужения до `char`), а `feof()` становится истинным только
**после** неудачного чтения.

Практическое следствие — карта без завершающего перевода строки молча теряет
последний ряд:

```
Файл "111\n222\n333"   (без \n в конце) -> распознано 2 строки   <-- ряд потерян
Файл "111\n222\n333\n" (с \n в конце)   -> распознано 3 строки
```

`map/0.txt` сейчас заканчивается переводом строки и читается корректно (9×12), но
любой редактор, сохраняющий без финального `\n`, **тихо срежет нижнюю стену карты**
— и игрок выйдет за границу мира. Ошибка проявится не в парсере, а где-то в логике
движения, то есть искать её будут долго.

**Решение:** `std::ifstream` + `std::getline` — обе ошибки исчезают, плюс снимается
ручное управление `FILE*`.

## 4. Логические баги

### H1. Имя персонажа присваивается наоборот — ввод игрока теряется
`andor.cpp:104-105`

```cpp
void set_start(string new_name) {
    new_name = name;    // <-- направление перепутано; надо name = new_name;
```

Параметр (ещё и переданный по значению) затирается полем, результат отбрасывается.
Проверено: после `set_start("Aragorn")` имя остаётся `"test"`. Игрок вводит имя в
`create()` — оно молча пропадает.

### H2. «Справка» выходит из игры, «Выход» не работает
`andor.cpp:181-190`

Пункты меню: `0` Новая игра, `1` Загрузить, `2` **Справка**, `3` **Выход**.
Обработчик:

```cpp
case 0: create(); gameplay(); break;
case 1: load();   gameplay(); break;
case 2: return(0);          // это "Справка" -> выходит из игры
// case 3 ("Выход") отсутствует -> ничего не делает, меню перерисовывается
```

Ветки смещены: «Справка» завершает программу, а «Выход» не завершает ничего.

### H3. Точка с запятой превращает цикл разбора карты в пустой
`andor.cpp:138`

```cpp
for (int i = 0; i < mline.size(); i++);   // <-- тело цикла пустое
```

Карта не парсится вообще; `base_map::cells`, `width`, `height` не заполняются.
Здесь это пока безобидно (парсер и не написан), но сам паттерн `for(...);`
компилятор не ловит — стоит включить `-Wempty-body` (входит в `-Wextra`).

### H4. Глобальный объект с именем `map` конфликтует со `std::map`
`andor.cpp:144` в сочетании с `using namespace std;` (`andor.cpp:24`)

```cpp
base_map map;   // глобальная переменная по имени map
```

Пока `<map>` не подключён, это компилируется. В момент, когда кто-нибудь добавит
`#include <map>` (или его затянет транзитивно), любое использование контейнера
ломается:

```
error: reference to 'map' is ambiguous
```

Мина замедленного действия: сломается не та строка, которую правили. Переименовать
в `world_map` / `current_map`, а `using namespace std;` — убрать (§5.10).

## 5. Архитектура, качество, инфраструктура

**5.1. Глобальное состояние.** `plr`, `enm`, `map`, `amap`, `mline` — глобальные
(`andor.cpp:95,142-145`). Для игры с сохранениями это ляжет плохо: состояние надо
уметь сериализовать, сбрасывать при «Новой игре» и не тащить между сессиями.
Стоит собрать в `struct GameState`, передаваемый явно.

**5.2. `mline` используется под две разные сущности.** Это и строки карты
(`load_map`, стр. 137), и пункты меню (`main`, стр. 180-184). Один глобальный
буфер под несвязанные данные — источник трудноуловимых наложений; уже сейчас
`create()` подменяет содержимое `mline` под ногами у `main()`.

**5.3. Магические числа вместо кодов тайлов.** В `map/0.txt` встречаются `0,1,3,5,6`,
а README описывает объекты глифами `[ ] [#] [∆] [*] [T] [L] [E/M] [@]`. Порядок в
README («воздух, стена, спальня, телепорт, табличка, предмет, моб, игрок»)
даёт согласованное соответствие: `0`=воздух, `1`=стена, `3`=телепорт, `5`=предмет,
`6`=моб — и карта ему действительно соответствует. **Но этот контракт нигде не
зафиксирован в коде.** Нужен `enum class Tile { Air=0, Wall=1, Bed=2, Teleport=3,
Sign=4, Item=5, Mob=6, Player=7 };` и раздел «формат карты» в README.

**5.4. Формат карты не выдержит дизайна из README.** Один символ на клетку не
вмещает то, что README требует от объектов: у телепорта есть локация и координаты
назначения, у предмета — код и количество, у моба — уникальный код, статы, инвентарь.
Сетка должна хранить только геометрию (воздух/стена), а объекты — отдельными
списками с координатами. Это решение лучше принять **сейчас**, до написания
загрузчика, а не переделывать потом.

**5.5. Пустые заглушки.** `render_map()` (148), `render()` частично (152),
`load_char()` (123), парсер карты (138). Из README не реализовано ничего:
ни таймеров, ни эффектов, ни квестов, ни зон спавна, ни инвентаря, ни боя.

**5.6. Неиспользуемый код.** `enemy enm;` (143) нигде не используется и не имеет
инициализаторов вовсе; `base_map amap` (145) объявлена, но не задействована;
`<math.h>` (22) не нужен.

**5.7. `int select = -1;` — мёртвое присваивание и затенение.** `andor.cpp:75`:
локальная переменная называется как сама функция и сразу перезаписывается на
строке 83. (Конфликта с POSIX `select(2)` тут нет — проверил, перегрузка
разрешается корректно, — но читаемости это не добавляет.)

**5.8. Меню поддерживает только цифры 1–9 и расходится с README.** `andor.cpp:80`:
условие `ch > 48+choices.size()` при более чем 9 пунктах начинает принимать `:`, `;`,
`<` вместо цифр. При этом README описывает навигацию стрелками + пробел —
`select()` этого не умеет. Для вкладок, инвентаря и торговли из README потребуется
полноценная навигация.

**5.9. `system("clear")` на каждый кадр.** `andor.cpp:87,153,185` — запуск
процесса оболочки на кадр: медленно, непортируемо и зависит от `PATH`.
Заменить на ANSI-последовательность `\033[2J\033[H`.

**5.10. `using namespace std;` в глобальной области.** `andor.cpp:24` — прямая
причина H4. При этом `toString` (65-70) написан с явным `std::`, то есть стиль
непоследователен.

**5.11. Всё передаётся по значению.** `WriteAllLines(string, vector<string>)`,
`ReadAllLines(string)`, `select(string, vector<string>)`, `print(string)`,
`set_start(string)` — копия вектора строк на каждый вызов. Нужен `const&`.

**5.12. Предупреждения компилятора.** Сейчас 4 × `-Wsign-compare`
(строки 31, 77, 80, 138) — знаковые `int`/`char` против `size_t`. Сборка должна
идти с `-Wall -Wextra`, а в CI — с `-Werror`.

**5.13. Отсутствует вся инфраструктура репозитория.**

| Чего нет | Зачем нужно |
|---|---|
| `Makefile` / `CMakeLists.txt` | Сейчас команду сборки знает только автор |
| `.gitignore` | Бинарники и `.o` попадут в репозиторий |
| CI (GitHub Actions) | B1 — ошибка компиляции — не дошла бы до `main` |
| Тесты | Парсер карты и сохранения тестируются тривиально |
| `LICENSE` | Права на использование не определены |
| Инструкция сборки в README | README — дизайн-док, как собрать и запустить, не сказано |

## 7. Что сделано хорошо

* **README — сильная сторона проекта.** Дизайн продуман до деталей: разделение
  базовых/боевых характеристик (`_hp` против `hp` как «база + скилы + экипировка»),
  порядок отрисовки слоёв, типы квестовых действий, состав сохранения. Многие
  проекты такого документа не имеют вовсе.
* **Разделение базовых и вычисляемых статов** (`andor.cpp:101` против `103`) —
  правильное решение, которое обычно приходит только после болезненного рефакторинга.
* **Секции `TODO` и `toolate`** в шапке файла честно фиксируют границы объёма —
  видно, что автор отделяет ближайшие задачи от «хотелок».
* **Кодировка карты уже согласована с порядком слоёв из README** (5.3) — то есть
  формат продуман, ему не хватает только фиксации в коде.

## Приложение. Как воспроизвести проверки

```bash
# B1 — ошибка компиляции
g++ -std=c++17 -Wall -Wextra -c andor.cpp
# andor.cpp:193:1: error: expected declaration before '}' token

# B2 — отсутствие conio.h на Linux
# andor.cpp:19:10: fatal error: conio.h: No such file or directory

# B3 — расхождение кодогенерации
printf 'void update(){while(1);}\n' > u.cpp
g++     -O2 -S -o - u.cpp | grep -A2 _Z6updatev   # цикл сохранён
clang++ -O2 -S -o - u.cpp | grep -A2 _Z6updatev   # тело удалено
```

C1, C2, C3, C5 и H1 проверены отдельными программами, воспроизводящими
соответствующие функции `andor.cpp` дословно; результаты приведены по месту.
